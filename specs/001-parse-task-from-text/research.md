# Research: Створення задачі з тексту

## Рішення

### Виклик моделі

- **Decision**: `app/parser.py` надає залежність `get_parser`, яка повертає малий parser object із методом `propose(text, today)`. Він використовує офіційний `openai` SDK для OpenAI напряму або OpenRouter через `base_url`; обидва варіанти мають спільний внутрішній формат пропозиції. SDK-клієнт створюється з `timeout=20.0` та `max_retries=0`.
- **Rationale**: Це відповідає існуючій залежності в `evals/run_eval.py`, забезпечує замінність парсера в `TestClient` і лишає рівно один контрольований retry в коді застосунку. SDK має власні retries за замовчуванням; їх треба вимкнути, інакше фактична кількість викликів не відповідатиме контракту.
- **Alternatives considered**: SDK defaults (не дають застосунку контролювати retry budget); окремі SDK для OpenRouter (дублюють транспорт і типи); безпосередній HTTP-клієнт (зайва залежність при наявному `openai`).
- **Source**: [openai-python: retries and timeouts](https://github.com/openai/openai-python#retries) описує `max_retries`, стандартні повтори й параметр timeout.

### Retry та класифікація помилок

- **Decision**: Парсер конвертує транспортні/SDK винятки у контрольований `ParseFailure` із причиною з переліку специфікації. Таймаут -> `timeout`, HTTP 429 -> `rate_limited`, помилки доступності/авторизації/сервера провайдера -> `provider_unavailable`; відмова -> `refused`; відсутній/неповний JSON -> `incomplete` або `invalid_structure`. Після виклику застосунок робить рівно один повтор тільки для `timeout` і `rate_limited`; якщо повтор також неуспішний, у fallback зберігається причина першого виклику. Інші причини одразу переходять у fallback. Жоден виняток провайдера не виходить як HTTP 500.
- **Rationale**: Явне відображення помилок гарантує передбачувану кількість спроб і стабільний API незалежно від деталей SDK.
- **Alternatives considered**: Дозволити SDK вирішувати повтори (порушує правило одного прикладного retry); повторювати всі помилки (зайві виклики для недетермінованих/постійних помилок); віддавати помилки провайдера клієнту (порушує fallback-контракт).

### Структура моделі та валідація

- **Decision**: Модельна пропозиція — окремий Pydantic v2 тип, не `Task` і не `TaskCreate`; вона включає `title`, `due_date`, `priority`, `tags`. Parser розрізняє транспортну структуру/відмову і повертає типізовану пропозицію. До запису код застосунку нормалізує й перевіряє назву (обрізати краї, 1–200 символів), пріоритет (лише `low|medium|high`; відсутній -> `medium`), дату (ISO календарна дата, сьогодні або майбутнє) і теги.
- **Rationale**: `Task` — збережена доменна сутність. Відокремлений тип не дозволяє SDK-відповіді напряму пройти в сховище й залишає правила застосунку незалежними від prompt.
- **Alternatives considered**: Передавати довільний `dict` до storage (слабша межа перевірки); використовувати `TaskCreate` як схему відповіді моделі (змішує HTTP input і зовнішню пропозицію).
- **Tag validation decision**: Явні `#hashtags` витягуються з вихідної фрази; модельні теги обмежуються п'ятьма у сумі, обрізаються, переводяться до нижнього регістру та дедуплікуються без урахування регістру. Порожній тег або тег, який не проходить правила доменної моделі, робить всю пропозицію семантично невалідною і запускає fallback; валідні модельні теги об'єднуються з явними хештегами. Під час fallback зберігаються лише явні хештеги. Це правило закриває невирішене припущення специфікації без мовчазного збереження некоректної модельної відповіді.

### Fallback

- **Decision**: Для допустимого запиту без валідної пропозиції зібрати `TaskCreate`: назва — обрізаний текст користувача (максимум 200 символів; якщо обрізання залишило порожній рядок, застосувати безпечне непорожнє представлення вихідної фрази), дедлайн — лише явна дата `YYYY-MM-DD`, що не раніше `today`, пріоритет `medium`, теги — лише явні хештеги після нормалізації. Зберегти через існуючий `TaskStore.add`; метадані шляху й причини лишаються у відповіді, не в `Task`.
- **Rationale**: Детермінований fallback не вигадує відносні дати й не довіряє модельним полям.
- **Alternatives considered**: Повертати помилку без створення задачі (суперечить AC та FR-010); використовувати модельні поля частково (ускладнює гарантію безпечного fallback).

### Годинник і тестова межа

- **Decision**: `app/clock.py:get_today()` повертає локальну `date` через `datetime.now(ZoneInfo("Europe/Kyiv")).date()`. Endpoint інжектує її через `Depends`; тести та eval підмінюють саме цю залежність. Endpoint-тести замінюють `get_parser` об'єктом-заглушкою через `app.dependency_overrides` і використовують ізольований `TaskStore`.
- **Rationale**: Один авторитетний, перевизначуваний час робить відносні дати відтворюваними й узгоджує тестовий та eval контракт.
- **Alternatives considered**: Використовувати системну UTC дату без адаптації (не Europe/Kyiv); читати час напряму в endpoint/parser (важко ізолювати в тестах).

### Модельні теги та explicit hashtag consistency

- **Decision**: Канонізація тегів відбувається один раз у застосунку перед побудовою `TaskCreate`; той самий результат повертається й зберігається. Перевищення ліміту тегів або відхилення окремого тегу спричиняє `invalid_semantics`, а не часткове прийняття відповіді.
- **Rationale**: Це детерміновано, помітно у fallback metadata й захищає гарантію про перевірку кожного поля.
- **Alternatives considered**: Мовчки відкидати лише поганий модельний тег (змішує успішний model path із неповною моделлю-відповіддю); частково зберігати теги з недовіреної пропозиції.
